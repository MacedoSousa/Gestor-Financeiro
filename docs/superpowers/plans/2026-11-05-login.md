# Login do casal — plano de implementação

> **Para agentes:** SUB-SKILL OBRIGATÓRIA: use superpowers:subagent-driven-development (recomendado) ou superpowers:executing-plans para executar este plano tarefa a tarefa. Os passos usam checkbox (`- [ ]`).

**Objetivo:** cada cônjuge entra com passkey (WebAuthn), ou com TOTP como alternativa, numa sessão de servidor guardada em cookie `HttpOnly`/`Secure`/`SameSite=Strict`, com bloqueio progressivo depois de 5 falhas. Um celular novo só entra com a aprovação do outro cônjuge ou com o código de recuperação. Um cônjuge logado pode gerar um novo código de recuperação, que invalida o anterior.

**Arquitetura:** tudo no módulo Identidade (schema `identidade`), mais o esquema de autenticação no Host.
- **Sessões:** ficam em `identidade.sessoes`. O cookie carrega só um token aleatório; o banco guarda o HMAC dele (`ICofre.IndiceCego`).
- **Credenciais:** passkey e TOTP ficam em `identidade.credenciais`, com o segredo TOTP cifrado.
- **Autorização de registro:** quem ainda não tem credencial recebe uma autorização curta (10 min), que permite registrar uma passkey ou um TOTP. Ela vem de uma de três fontes: primeiro acesso por CPF + senha, pedido de dispositivo aprovado pelo cônjuge, ou código de recuperação.
- **Rotas protegidas:** toda rota de `/api/v1` exige sessão, exceto as listadas como anônimas.

**Tecnologias:** .NET 10, EF Core 10 + Npgsql, Fido2 4.3.1 (Fido2NetLib), Otp.NET 1.4.1, `System.Formats.Cbor` (só nos testes), xUnit + Testcontainers (projeto de integração já existente), React 19 + TanStack Query, `@simplewebauthn/browser` 13.3.0, `qrcode` 1.5.4 (+ `@types/qrcode` 1.5.6).

**Especificação:** `docs/adr/0011-sessao-em-cookie.md`, `docs/adr/0006-duckdns.md` (camadas de proteção), `docs/adr/0005-envelope-encryption.md`, `docs/SPEC.md` (tarefa "Login com sessão em cookie"), `docs/design/README.md` + `docs/design/telas/Main.dc.html`, `CLAUDE.md`, `.claude/rules/backend.md`, `.claude/rules/frontend.md`. Plano anterior, com as convenções já usadas: `docs/superpowers/plans/2026-11-05-cadastro-do-casal.md`.

## Decisões já tomadas

1. **Primeiro acesso por CPF + senha** (escolha do usuário). A senha do cadastro é conferida abrindo o envelope `USUARIO` desse cônjuge (Argon2 padrão). Uma senha errada conta como falha para o bloqueio.
   - **Fecha para sempre** (ajuste do usuário): quando o cônjuge confirma o primeiro dispositivo (passkey registrada ou TOTP confirmado), grava-se o marcador `usuarios.primeiro_acesso_encerrado_em`.
   - A partir daí o primeiro acesso responde `403` sem testar a senha, mesmo que depois ele remova todas as credenciais.
   - A regra olha o marcador, nunca a contagem de credenciais atuais.
2. **Bloqueio progressivo** (escolha do usuário):
   - Na 5ª falha seguida, a conta é bloqueada por 15 min.
   - Cada novo bloqueio dobra o tempo anterior, até o teto de 24 h.
   - Um login certo zera as falhas seguidas e a contagem de bloqueios.
   - O outro cônjuge, logado e com confirmação recente, pode destravar na hora.
   - Contam como falha: código TOTP errado, senha errada no primeiro acesso, código de recuperação errado, e assinatura de passkey inválida quando a credencial é conhecida.
3. **Duração da sessão** (escolha do usuário):
   - A sessão expira depois de 7 dias sem uso e, de qualquer forma, 30 dias depois de criada.
   - Ações sensíveis exigem confirmação recente: passkey ou TOTP confirmados nos últimos 5 minutos (`POST /api/v1/auth/confirmar`). São elas: aprovar dispositivo, destravar o cônjuge, gerar código de recuperação, adicionar e remover credencial.
4. **Aprovação de celular novo por código de 6 dígitos** (escolha do usuário):
   - O celular novo informa o CPF e recebe um pedido, que vale 10 min, com um código de 6 dígitos.
   - O cônjuge logado vê o pedido em Dispositivos, confere o código e aprova.
   - O celular novo consulta o estado do pedido com um GET que **só devolve o status**, sem efeito colateral, e tem limite próprio no Caddy de 60/min por IP (ajuste do usuário).
   - Quando o status for `APROVADO`, o celular resgata a autorização de registro com um POST separado.
   - O pedido não pode ser aprovado pelo próprio dono.
5. **Código de recuperação como alternativa à aprovação:**
   - CPF + código de recuperação, conferido abrindo o envelope `RECUPERACAO` com `EnvelopeDeChaves.CanonizarCodigo`, dá a autorização de registro.
   - Usar o código **gira o código na hora**: o envelope anterior é marcado como removido (soft delete), um novo é gravado na mesma transação, e o código novo é mostrado uma vez.
6. **Novo código de recuperação para um cônjuge logado:** `POST /api/v1/casal/codigo-recuperacao`, com confirmação recente. Na mesma transação, o envelope `RECUPERACAO` ativo é marcado como removido e um novo é gravado. A resposta traz o código uma vez, com `no-store`. Isso também cobre o caso de um `201` do cadastro que se perdeu.
7. **Escolhas técnicas deste plano (revisar):**
   - **Passkey sem digitar usuário:** credencial descobrível (`residentKey: required`, `userVerification: required`, `attestation: none`).
   - **TOTP:** pede CPF + código. Padrão RFC 6238 (SHA-1, 6 dígitos, 30 s), aceita ±1 passo, e um passo já usado é rejeitado (sem reuso).
   - **Desafios WebAuthn:** guardados em `IMemoryCache` por 5 min. É um processo só; um restart invalida desafios pendentes.
   - **Autorização de registro:** também em `IMemoryCache`, por 10 min, ligada a um cookie próprio.
   - **CSRF:** `SameSite=Strict` mais o cabeçalho `X-Requested-With: gestor-web`, que é obrigatório em todo método que não seja GET/HEAD. Sem ele, `403`.
   - **Sessão e TOTP sem nada em claro** (ajuste do usuário): `identidade.sessoes` guarda só `token_hmac`, sem token, IP nem user agent. O segredo TOTP só existe em `credenciais.segredo_cifrado` (via `ICofre.Cifrar`), e só a URI `otpauth` do registro o leva ao navegador.
   - **Auditoria das sessões:** `sessoes.ultimo_uso_em` só é regravado quando tem mais de 1 h, para não inundar a trilha de auditoria (toda tabela nova passa por `audit.proteger`).
   - **Último acesso:** um cônjuge não pode remover a própria última credencial ativa (`409`).
   - A porta 443 **continua fechada**. Abrir é decisão do usuário depois do merge (ADR-006).

## Restrições globais

- Regras do `CLAUDE.md` valem integralmente: sem DELETE físico (logout e revogação são `is_deleted = true`); auditoria só por trigger; índice único parcial `WHERE NOT is_deleted`; tabela nova chama `SELECT audit.proteger('identidade.<tabela>');` na migração que a cria; filtros `SoftDelete` e `Casal` nunca desligados (`IgnoreQueryFilters([Filtros.Casal])` só onde o casal ainda não é conhecido: login e pedido de dispositivo, como já faz `ConsultaDeUsuarios.ObterPorTelefoneAsync`).
- **Migração nova:** `db/migrations/V0002__login.sql`. Nunca editar a V0001.
- **Dado sensível:**
  - O segredo TOTP fica em `segredo_cifrado`, com AAD `identidade.credenciais|segredo_cifrado|{id:N}`.
  - Os tokens de sessão e de pedido nunca são gravados em claro: só `*_hmac`, via `ICofre.IndiceCego(token, "sessao")` e `ICofre.IndiceCego(token, "pedido")`.
  - O CPF é buscado por `cpf_hmac` com o propósito `"cpf"`.
- **Nada pessoal em log, exceção ou erro:** nem CPF, código, senha, token, segredo TOTP ou credential id. Logar só ids internos.
- **Cookies:**
  - `__Host-gf_sessao`: sessão; `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, sem `Domain`, com `Max-Age` igual ao que falta para a expiração absoluta.
  - `__Host-gf_pedido`: pedido de dispositivo, 10 min, mesmos atributos.
  - `__Host-gf_registro`: autorização de registro, 10 min, mesmos atributos.
- **Tokens:** 32 bytes de `RandomNumberGenerator`, em base64url.
- **WebAuthn:**
  - `Seguranca:WebAuthn:RpId`: em dev `localhost`; em produção, o valor de `DOMINIO`.
  - `Seguranca:WebAuthn:Origens` (lista): em dev `http://localhost:5173`; em produção, `https://<DOMINIO>`.
  - `ServerName`: `Gestor Financeiro`.
  - `user.name` e `user.displayName`: o apelido (primeiro nome), nunca o CPF.
  - user handle: os 16 bytes de `usuario.Id`.
- **Tempos** (constantes nomeadas, um único lugar): falhas para bloquear `5`; bloqueio base `15 min`; teto `24 h`; sessão parada `7 dias`; sessão absoluta `30 dias`; confirmação recente `5 min`; pedido `10 min`; autorização de registro `10 min`; desafio WebAuthn `5 min`; regravação de `ultimo_uso_em` `1 h`.
- **Mensagens fixas** (cópia exata):

  | Situação | Status | Mensagem |
  | --- | --- | --- |
  | Falha de login | `401` | `Não foi possível entrar. Confira os dados e tente de novo.` |
  | Conta bloqueada | `423` | `Conta bloqueada por excesso de tentativas. Tente mais tarde ou peça ao outro cônjuge para destravar.` |
  | Sem confirmação recente | `403` | `Confirme sua identidade para continuar.` |
  | Primeiro acesso para quem já tem credencial | `403` | `Este acesso já foi configurado. Entre com sua passkey ou TOTP.` |
  | Remover a última credencial | `409` | `Você precisa manter pelo menos uma forma de entrar.` |

  Para CPF inexistente, a API responde exatamente como para senha ou código errado.
- **Tempo:** usar `TimeProvider` (já registrado); os testes substituem por `RelogioFixo`.
- **Contrato:** mudou o contrato → `dotnet build backend/src/Host/GestorFinanceiro.Api && npm --prefix frontend run gen:api` no mesmo commit.
- **Antes de cada commit:** `dotnet test backend/GestorFinanceiro.slnx` verde (precisa de Docker) e 0 avisos em `dotnet build backend/GestorFinanceiro.slnx --no-incremental`.
- **Commits:** curtos, em pt-BR, terminando com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Branch `fase-1/login`, criada a partir da `main`.

## Foco da revisão

1. **Reuso de código TOTP dentro da janela de ±1 passo** → o segundo uso do mesmo código é `401` e conta como falha. Teste: `Codigo_totp_reusado_e_rejeitado` (Tarefa 4).
2. **Falhas de tipos diferentes somam para o bloqueio** (2 TOTP + 2 senha + 1 recuperação), e com a conta bloqueada nem o código certo entra (`423`). Teste: `Falhas_de_tipos_diferentes_somam_e_bloqueio_vale_ate_para_codigo_certo` (Tarefa 6).
3. **Um cônjuge aprovar o próprio pedido de celular novo** → `403`; o pedido continua pendente. Teste: `Dono_nao_aprova_o_proprio_pedido` (Tarefa 6).
4. **Sessão encerrada em outra aba ou expirada** → `401`; o front vai para `/entrar` uma vez, sem laço de redirecionamento. Testes: `Sessao_encerrada_responde_401` (Tarefa 2) e verificação no navegador (Tarefa 8).
5. **Cônjuge que remove todas as credenciais tenta o primeiro acesso de novo com a senha** → `403`; o caminho passa a ser o celular novo. Teste: `Primeiro_acesso_continua_fechado_depois_de_remover_credenciais` (Tarefa 7).
6. **Remover a própria última credencial** → `409`, e a credencial continua ativa. Teste: `Nao_remove_a_ultima_credencial` (Tarefa 7).
